# ТЗ: ML-прогноз спроса (этап 8)

Цель этапа — обучить двухэтапную LightGBM из текста ВКР («Модель
прогнозирования востребованности»), честно сравнить её с базовыми оценками и
подключить к Planner вместо EWMA. Автор должен воспроизвести обучение и
объяснить прогноз конкретного объекта.

Ввод модели по расписанию, журнал версий, горячая замена и откат при
устаревании — этап 9. Итоговое сравнение политик по задержке — этапы 10–11.

## Принятые решения

- Модель: классификатор `binary` даёт `p = P(N ≥ 1)`, регрессор `poisson`
  обучается только на `N ≥ 1` с меткой `N − 1`, `m = 1 + ŷ`, `N̂ = p·m`
  (формулы `count` и `hurdle`). Признаки — `features-v1` из Feature Builder,
  горизонт H = 1 ч, текущий класс и задержка в признаки не входят.
- Обучение на Python, применение в Go через `leaves`. Функции связи (sigmoid,
  exp) применяются в Go явно, а не полагаются на автоматику `leaves`; это уже
  проверено спайком (ветка `claude/wonderful-proskuriakova-bbe2b4`).
- Разбор и демонстрация — Jupyter notebook. Вся логика — в Python-пакете
  `services/sppr/ml`, notebook только вызывает его и рисует; те же шаги
  запускаются из `make` без notebook.
- Данные: модель обучается отдельно на каждом источнике (как будет в живой
  системе — на истории своего хранилища). Источники:
  - синтетика этапа 6: шесть сценариев, seed 0, профиль приёмки (10 000
    объектов по 1 МиБ, 20 чтений/с, срез каждые 300 с);
  - Meta CDN (CacheLib, 2023, неделя, выборка 20 %);
  - IBM Cloud Object Storage (трассы SNIA, 2021);
  - IBM Docker Registry (Anwar и др., FAST 2018, 75 дней).
  Трассы приводятся к формату этапа 6 (`catalog.json` + `events.jsonl`), дальше
  тот же Feature Builder, те же правила меток и разбиения по времени.
- Сценарий от LLM-агентов — не здесь, а в этапе 10 (агенты пишут описание
  поведения пользователей один раз, генератор воспроизводит его по seed).
- Срезы обучения прореживаются до одного в 15 мин; validation и test остаются
  полными. Проверка на validation: качество не хуже, чем с полными срезами
  (см. «Ресурсы»).
- Модель попадает в SPPR файлами: `PLANNER_PREDICTOR=ewma|lgbm` и
  `PLANNER_MODEL_DIR` с двумя моделями и манифестом. Реестр версий в БД — этап 9.

## Разбиение и честность проверки

Периоды относительно начала истории (как в этапе 6): train `[0, 48 ч)`,
validation `[48, 72 ч)`, test `[72 ч, конец)`. Метка не пересекает границу
периода (`purged`). Для трасс длиной не 7 суток периоды задаются в долях и
записываются в манифест до обучения.

- Ранняя остановка бустинга — по последним 8 ч train (`train-tail`), а не по
  validation.
- Гиперпараметры выбираются по validation из небольшой заранее заданной сетки
  (число листьев, скорость обучения, минимальный размер листа, регуляризация);
  критерий — `Cov_K`, при равенстве — Brier.
- Монотонные отображения базовых оценок (возраст, давность → ожидаемые чтения)
  подбираются на train.
- Test в этапе 8 не открывается: ни метрик, ни графиков. Код, который читает
  test, должен требовать явного флага и в этапе 8 не вызываться.

## Метрики (на validation, по каждому источнику)

- Классификатор: PR-AUC, Brier.
- Прогноз числа чтений: `Cov_K` по формуле `capture` — доля фактических
  чтений, пришедшихся на K объектов с наибольшим `N̂`; K = вместимость HOT
  (921 объект для профиля приёмки, для трасс — та же доля 9,21 % каталога),
  плюс кривая `Cov_K` по K. Дополнительно — пуассоновское отклонение и MAE.
- Те же метрики для базовых оценок: EWMA, частота (чтения за 24 ч в пересчёте
  на H), возраст, давность. Для Brier у базовых оценок `p = 1 − e^{−N̂}`.
- Разброс: доверительные интервалы bootstrap по моментам среза.
- Отсутствие улучшения не скрывается: таблица показывает разность с лучшей
  базовой оценкой по каждому источнику, включая `uniform`, где выигрыша быть
  не должно.

## Контракт модели (общий для частей 1 и 2)

Каталог модели:

- `classifier.txt`, `regressor.txt` — текстовый формат LightGBM;
- `manifest.json`: `model_version`, `method_version` (`lgbm-hurdle-v1`),
  `feature_rules_version` (`features-v1`), `feature_names` в порядке столбцов,
  `horizon_seconds`, версии LightGBM/Python/numpy, гиперпараметры, интервалы
  train/validation, источник и SHA-256 данных, метрики validation, SHA-256
  обоих файлов модели;
- `parity.json` — контрольные строки: признаки, сырые выходы обеих моделей,
  `p`, `m`, `N̂` из Python. Обязательно есть нули, популярные объекты,
  отсутствующие значения (`null` → NaN), крайние значения.

### Схема файлов экспорта v1

Имена полей фиксированы для независимой реализации Go и Python.
`manifest.json` — JSON-объект:

| Поле | Тип / значение |
|---|---|
| `model_version` | непустая строка, идентификатор конкретного артефакта |
| `method_version` | `"lgbm-hurdle-v1"` |
| `feature_rules_version` | `"features-v1"` |
| `feature_names` | массив строк в порядке столбцов, строго как ниже |
| `horizon_seconds` | целое положительное число, совпадает с `PLANNER_HORIZON` |
| `lightgbm_version`, `python_version`, `numpy_version` | строки версий экспортёра |
| `hyperparameters` | объект параметров обучения (при разных параметрах — вложенные объекты `classifier` и `regressor`) |
| `train_interval`, `validation_interval` | объекты `{"start": "RFC3339 UTC", "end": "RFC3339 UTC"}`, интервалы `[start,end)` |
| `source` | строка с идентификатором источника и описанием входа, к которому относится `data_sha256` |
| `data_sha256` | SHA-256 байтов входного файла срезов; для набора файлов — SHA-256 входного dataset manifest, перечисляющего их хеши |
| `validation_metrics` | объект метрик validation; test сюда не входит |
| `classifier_sha256`, `regressor_sha256` | SHA-256 исходных байтов соответствующего `.txt`, hex из 64 символов |

Порядок `feature_names` (тот же в заголовках обоих `.txt`):

```json
["log_size", "age_seconds", "overwrites_24h", "last_read_seconds",
 "previous_read_seconds", "reads_5m", "reads_1h", "reads_6h", "reads_24h",
 "ewma_1h", "ewma_6h", "short_long_ratio", "reads_day_ago", "mean_read_fraction",
 "bucket_reads_1h", "bucket_active_fraction", "observed_seconds"]
```

Go принимает стандартные деревья LightGBM text v3/v4, objective классификатора
строго `binary sigmoid:1`, регрессора — `poisson`, один выход. Linear trees и
random forest не поддерживаются. Преобразование заголовка `version=v4` → `v3`
в памяти нужно для закреплённой версии `leaves`; SHA-256 проверяется до него.
Модели загружаются с отключёнными преобразованиями `leaves`, а Go явно считает
`p = sigmoid(classifier_raw)`, `m = 1 + exp(regressor_raw)`, `expected_reads = p*m`.

`parity.json` — объект с непустым массивом `rows`. Каждая строка содержит:

- `name`: строковое описание случая;
- `features`: объект со всеми 17 именами, значения — числа или `null` (Go
  переводит `null` в NaN, не в ноль);
- `want`: обязательные числовые `classifier_raw`, `regressor_raw`,
  `probability` (= p), `conditional_reads` (= m), `expected_reads` (= N̂).
  Экспортёр может также писать `excess_reads` (= exp(regressor_raw));
  дополнительные метаданные в `meta` разрешены.

Допуск загрузчика для каждого обязательного выхода:
`abs(go − python) <= 1e-9 * abs(python)`. Нулевой эталон требует точного нуля.
Допуск закреплён тестами внутри/снаружи границы; NaN/Inf в выходах запрещены.
Нужны контрольные строки с нулями, востребованными объектами, `null` и крайними
значениями; они проверяют применение модели, а не оценивают качество обучения.

[Фикстура Go](../services/sppr/internal/service/predictor/lgbm/testdata/manifest.json)
— перенесённая модель spike, не результат обучения и приёмки этапа 8.
Её исходные интервалы не записаны, поэтому только в этой исторической фикстуре
`start/end` равны `null`, `validation_metrics={}`; версии, параметры и хеш данных
перенесены из `parity.meta`. Новые экспорты части 2 записывают реальные интервалы
и метрики validation. Содержимое provenance Go хранит как метаданные: загрузчик
проверяет их наличие, а качество и корректность обучения оценивает offline-процесс.

## Часть 1. Go-предиктор и подключение (Codex)

- Перенести `internal/service/predictor/lgbm` из спайка на текущий `main`,
  реализовать `service.Predictor` (`MethodVersion`, `Predict(snapshot, horizon)`).
  Вектор признаков строится из `model.Features` в порядке `feature_names` из
  манифеста; несовпадение имён или версии правил → ошибка загрузки.
- Загрузка проверяет SHA-256 файлов, версию правил признаков, горизонт
  (`horizon_seconds` = `PLANNER_HORIZON`, иначе отказ), прогон `parity.json`
  с допуском 1e-9 относительной ошибки (допуск фиксируется в тесте).
- Прогноз с NaN/Inf или отрицательный → ошибка для этого объекта (Planner уже
  трактует ошибку как `no_forecast`).
- `PLANNER_PREDICTOR=ewma|lgbm`, `PLANNER_MODEL_DIR`. При ошибке загрузки SPPR
  стартует на EWMA, `/api/planner/status` и панель показывают метод,
  версию модели и причину отката. Ревизия плана хранит `method_version` и
  `model_version`.
- Объяснение рекомендации для ML: `p`, `m`, `N̂`, и для сравнения оценка EWMA
  (текст ВКР: «оценка EWMA для сравнения»). Поля добавить в объяснение, панель
  показывает их.
- Тесты: паритет на фикстуре спайка, отказ при несовпадении версии, имени
  признака, горизонта, хеша; откат на EWMA; Planner с ML на моках.

## Расхождения с текстом

- Базовые оценки «возраст» и «давность» переводятся в ожидаемые чтения монотонной
  функцией, подобранной на train, а не на периоде настройки: validation уже
  выбирает гиперпараметры, второй подбор на нём завысил бы базовые оценки.
- Ранняя остановка бустинга — по последним 8 ч train, затем модель обучается на
  всём train с найденным числом деревьев; validation в обучение не входит.
- `Cov_K` агрегируется как отношение сумм по всем моментам среза; равные прогнозы
  упорядочиваются случайно с фиксированным seed. Сравнение с базовой оценкой —
  парный bootstrap разности по моментам среза.
- При ~7 чтениях в час на объект (и рабочая выборка, и профиль приёмки) в
  сценариях decay, burst и uniform почти нет нулевых меток: PR-AUC и Brier там
  вырождаются, решает `Cov_K`. Текст ВКР («у большинства объектов чтений нет»)
  к этим сценариям не относится; это нужно отразить при описании профиля.
- Рабочая выборка этапа — 1000 объектов (`examples/data/medium.json`) с той же
  интенсивностью на объект, что у профиля приёмки; профиль приёмки и трассы —
  часть 4, вместе с проверкой прореживания и ресурсов.

## Что понять автору (из плана)

Что учится в деревьях; зачем две модели; что значат PR-AUC, Brier и `Cov_K`;
почему качество прогноза — не то же самое, что выигрыш по задержке.
