# Этап 5: реализация и границы проверки

Контракт: [history-completeness-spec.md](history-completeness-spec.md).
Реализованы heartbeat protobuf/Go/Python, публикация Gateway и graceful closing,
приём и идемпотентность SPPR, хвостовые/потерянные gaps, общая W, Planner на W,
status/admin, конфигурация и шестисценарный smoke.

## Решения в местах, не определённых спецификацией

1. Ветка `feat/history-completeness` уже существовала ровно на исходном HEAD
   `dbb0951`. Изменения и коммиты подготовлены в локальном клоне под `build/`,
   итоговый bundle содержит эту ветку. Общий Git не изменяется, push/PR нет.
2. Сигнатура общего `kafka.Producer.Send` сохранена. Заголовки и канал подтверждения
   shutdown передаются через контекст адаптера. Gateway включает successes;
   `LogResults` вычитывает оба канала, ошибки сохраняют topic/error в логах.
3. Чтобы closing отправлялся после дотправки буфера, shutdown после HTTP drain
   прекращает периодическую задачу, подтверждает обычный heartbeat каждого
   топика, затем подтверждает closing каждого топика. Подтверждений на HTTP-пути
   нет. При ошибке/таймауте shutdown не сообщает успешное закрытие потока.
   Если HTTP не успел завершить запросы, используется Abort без closing: поздние
   операции больше не публикуют в уже закрываемый producer.
4. Для повторов heartbeat добавлена таблица receipts с исходным payload hash.
   Повтор тех же байтов идемпотентен и при другом Kafka offset. Неизвестный
   `event-type` отклоняется без бесконечного retry, как некорректное сообщение.
5. Для неизвестного числа потерянных событий используется `last_sequence = NULL`,
   а `first_sequence` остаётся следующим номером потока. Down отказывается
   удалять такие доказательства: пока неизвестные gaps существуют, старую схему
   нельзя восстановить без потери смысла. Это ограничение указано в runbook.
6. Для первого heartbeat пустого потока сохраняется `first_heartbeat_at`.
   `created_at` нужен для timeout потока, который ни разу не прислал heartbeat;
   события этот timeout не продлевают. Старым потокам миграция не присваивает W.
   При неизвестной границе lost gap начинается от первого события/регистрации.
7. Буквальное консервативное чтение пункта 4 спецификации: однажды потерянные
   номера не становятся полученными после следующего heartbeat. Пока поток
   содержит потери, complete_until остаётся временем последнего события;
   если ни одного события не получено, граница неизвестна. Gaps сохраняются.
   Закрытый/lost поток не открывается поздним трафиком, но точные повторы уже
   записанных событий/heartbeat продолжают дедуплицироваться. После длительного
   отказа Kafka нужен новый stream_id через рестарт Gateway.
8. Открытый поток с неизвестной границей удерживает общую W неизвестной.
   При отсутствии открытых максимум берётся только из известных границ закрытых;
   если таких нет, W неизвестна. Потерянные входят также в число закрытых.
   Gaps без известного after_time покрывают весь запрошенный интервал с его начала,
   чтобы расширение истории до рождения версии не скрывало первый пропуск.
9. Для произвольной W mutable минутных агрегатов недостаточно: SQL сначала
   отбирает дедуплицированные access_events по `[from, W)`, затем группирует по
   минутам. Точность времени внутри минуты остаётся прежней точностью признаков;
   чтения на/после W в них не попадают. Отдельно считываются gaps за полные 24 ч
   до выбранной W. В статусе и расчёте момент фиксируется на выбранной W.
10. Metadata не предоставляет снимок каталога на прошлый момент W. Если версия
    каталога создана позже W, весь план консервативно непригоден (`unobserved`),
    пока heartbeat не догонит эту версию. Правило начала истории сохранено,
    `assumeCaughtUp` удалён.
11. Gaps за 24 ч считаются по `before_time`; lost — подмножество closed.
    Карточки текущих объектов добавлены на страницу состояния, потому что при
    неполной истории готовых рекомендаций может не быть. API возвращает ту же
    информацию в `history`, `history_lag_seconds`, `objects`.
12. Smoke работает на выделенном стенде, сам останавливает Kafka и kill/stop
    Gateway, в defer пытается вернуть оба сервиса. Локальная Make-цель явно
    выключает admin auth только для тестового стенда, задаёт heartbeat 1 с и
    lost timeout 30 с. Для уже защищённого стенда используется access token.
    Outage должен завершиться раньше lost timeout с учётом Docker stop/start.
13. Репозиторий генерирует Python bindings, но ранее не имел target для events.
    Добавлен `generate-events-py` через встроенный Python generator protoc:
    у events нет gRPC service. Go/Python events сгенерированы, не редактировались
    вручную. Изменения версий генератора в посторонних protobuf outputs исключены.

## Проверки

- `go vet ./...` из Gateway, SPPR и `shared/pkg/go-kit`: успешно.
- `go test ./...` из Gateway и SPPR запускались. В sandbox остаются ошибки
  существующих TCP/httptest проверок (`bind: operation not permitted`):
  Gateway `internal/app`, `internal/handler/httpapi`; SPPR `internal/app`.
  Остальные пакеты проходят. Это не полный зелёный прогон.
- `go test ./...` из `shared/pkg/go-kit`: успешно.
- `go test -race` для Gateway config/access producer, SPPR config/ingestor/
  consumer/event/history/planner/API/admin и общего async producer: успешно.
- Интеграционные пакеты SPPR с `-tags=integration -run '^$'` компилируются.
  Новые PostgreSQL tests включены в существующий integration suite, но проверки
  БД пропущены: `SPPR_TEST_PG_DSN` не задан; доступной БД не обнаружено
  (`127.0.0.1:5436`, Unix socket `/tmp:5432`).
- `cmd/smoke-history` собирается; Make-цели проверены через `make -n`.
  Docker smoke не запускался: доступ к Docker socket запрещён sandbox.
- `make generate-go`, `make generate-events-go generate-events-py` успешны;
  Python events проходят `py_compile`. Полный `make generate` доходит до Python
  остальных сервисов и останавливается из-за отсутствующего `grpc_tools`.
  Сетевая установка инструментов недоступна. Runtime Python import не проверялся.
- `git diff --check`: успешно.

Исходные логи проверок находятся в `build/history-*.log` (локальные артефакты).
Остаются внешние проверки: полный сетевой Go suite, PostgreSQL integration,
шесть сценариев Docker smoke и полный `make generate` с grpcio-tools.
