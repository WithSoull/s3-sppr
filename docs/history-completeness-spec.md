# Этап 5: полнота истории обращений (heartbeat и отметка W)

Цель — чтобы SPPR знал, до какого момента история чтений полна, и отличал «чтений
не было» от «история неполна». Сейчас Planner считает историю полной до момента
расчёта (`assumeCaughtUp` в `planner/snapshot.go`), а хвост потока упавшего
Gateway теряется незаметно ([спека Kafka](kafka-spec.md), раздел 7).

## Решения

1. **Heartbeat в том же потоке.** Каждый поток Gateway (`gateway_id`, `stream_id`,
   один на топик) раз в `ACCESS_HEARTBEAT_INTERVAL` (по умолчанию 5 с) отправляет
   `events.v1.StreamHeartbeat{position (sequence = последний выданный номер),
   at, closing}` в свой топик с тем же ключом `{gateway_id}/{stream_id}` и
   заголовком Kafka `event-type: heartbeat`. Отправка — под мьютексом потока,
   как событие: при идемпотентном producer и `MaxOpenRequests = 1` heartbeat
   приходит после всех событий с номером ≤ sequence. Номер heartbeat не тратит.
   События без заголовка — прежние `ObjectRead` / `ObjectWritten`.
2. **Завершение потока.** При graceful stop Gateway после дотправки буфера шлёт
   heartbeat с `closing = true`. Закрытый поток больше не задерживает W.
3. **Хвост.** Heartbeat с `sequence > last_sequence` потока означает потерю
   событий `last_sequence+1 … sequence`: Ingestor пишет пропуск в
   `ingestion_gaps` (`after_time` — время последнего события, `before_time` —
   `at` heartbeat), как для пропуска между событиями.
4. **Полнота потока.** `complete_until` потока — `at` последнего heartbeat, если
   на тот момент все номера до его `sequence` получены (иначе — время последнего
   события). Хранится в `ingestion_streams` вместе с `last_heartbeat_at`,
   `closed_at`, `lost_at`.
5. **Потерянный поток.** Открытый поток без heartbeat дольше
   `INGEST_STREAM_LOST_AFTER` (по умолчанию 30 с = 6 интервалов) объявляется
   потерянным (упал Gateway): в `ingestion_gaps` пишется пропуск
   `[complete_until, lost_at)` с неизвестным числом событий, поток закрывается.
   Проверяет фоновая задача Ingestor; время — управляемые часы в тестах.
6. **Отметка W.** `W = min(complete_until)` по открытым потокам; если открытых
   нет — `max(complete_until)` закрытых, но не позже момента, когда последний
   поток закрылся. Нет ни одного потока — полнота неизвестна. `last_event_at`
   одного потока W не задаёт.
7. **Planner считает на момент W.** Расчёт идёт на `at = W` (а не «сейчас»);
   если `now − W > PLANNER_MAX_HISTORY_LAG` (по умолчанию 60 с) — план не
   строится, статус «история отстаёт» с величиной отставания. Пропуски, как и
   сейчас, делают признаки, чьё окно их задевает, непригодными
   (консервативно: неизвестное число событий — не ноль). `assumeCaughtUp`
   удаляется; правило «начало истории не позже создания самой старой версии»
   остаётся, т. к. Gateway публикует запись версии после её создания.
8. **Метки для обучения.** Метка среза `t` пригодна, только если `W ≥ t + H` и
   в `(t, t+H]` нет пропусков — это уже делает `features.Quality`; этап 9 берёт
   границы из той же `Coverage`.
9. **Видимость.** `/api/planner/status` и `/admin` показывают W, отставание,
   число открытых/закрытых/потерянных потоков и пропуски за 24 ч; для каждого
   объекта в карточке различаются «чтений нет» (история полна, событий нет) и
   «история неполна» (причина качества признаков).

## Что не меняется

Контракт `ObjectRead`/`ObjectWritten`, дедупликация по `(gateway, stream,
sequence)` + `payload_hash`, commit-before-ack, ограниченный буфер Gateway и то,
что ошибка Kafka не срывает клиентский запрос. Копирования исполнителя идут
Storage → Storage мимо Gateway и спросом не считаются.

## Проверка

- Unit: номера и heartbeat под одним мьютексом; heartbeat не тратит номер;
  closing при остановке; Ingestor — хвостовой пропуск по heartbeat, поток без
  heartbeat объявляется потерянным по управляемым часам, расчёт W для открытых /
  закрытых / потерянных потоков; повтор heartbeat идемпотентен.
- Integration (`make test-sppr-integration`): схема, хранение
  `complete_until`/`closed_at`/`lost_at`, `Coverage` из БД.
- Planner: расчёт на `at = W`; отставание больше порога — план не строится;
  пропуск в окне — признаки непригодны.
- Стенд, `make smoke-history` (новая цель, по образцу smoke-planner):
  1. GET → событие и рост W без новых чтений (heartbeat);
  2. повтор события не удваивает спрос;
  3. Kafka остановлена → GET работают, после возврата пропуск виден;
  4. `docker kill` Gateway → поток объявлен потерянным, пропуск записан, W после
     рестарта снова растёт;
  5. `docker stop` Gateway → поток закрыт без пропуска;
  6. статус показывает «история неполна» при пропуске и «чтений нет» для
     объекта без чтений при полной истории.

  CLAUDE.md.
