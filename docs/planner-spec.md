# ТЗ: Planner, команды администратора и панель (этап 7)

Этап 7 замыкает рабочий цикл на базовой политике EWMA: чтения → прогноз →
план с объяснением → решение администратора → исполнитель 4.3 → чтение из HOT.
ML (этап 8) потом подставляется вместо EWMA без изменения Planner.

Источник требований — текст ВКР: постановка задачи размещения (формулы
`service_time`, `latency`, `gain`, `objective`, `capacity`, `budget`), алгоритм
формирования плана, объяснение рекомендаций, административный API, руководство
администратора, таблица исключительных ситуаций, случаи проверки C-01…C-04, C-06.
Если ТЗ расходится с текстом, прав ТЗ, а расхождение записывается в раздел
«Расхождения с текстом» ниже.

## Принятые решения

- Права проверяются через существующие Auth и AuthZ: `Auth.ValidateToken` для
  access token и `AuthZ.Check` с действием `ADMIN` на ресурсе `system:placement`.
  Это касается и JSON API, и HTML, включая уже существующий `/api/migration`.
- План считается по таймеру (`PLANNER_INTERVAL`, по умолчанию 300 s) и по кнопке
  «Рассчитать план». Каждый расчёт создаёт новую ревизию. Подтвердить можно только
  последнюю ревизию, остальные получают `PLAN_STALE`.
- Пока нет отметки полноты истории (этап 5), Planner опирается на
  `DataQuality`, которую уже вычисляет Feature Builder, и на `ingestion_gaps`.
  Когда этап 5 появится, сменится только источник `Coverage`, код Planner не меняется.
- Нетекущие версии в HOT — кандидаты только на выселение в COLD, их прогноз 0.
- Два разных параметра, которые раньше оба называли Δmin:
  - **минимальный интервал** между переносами одной версии — уже есть в исполнителе
    (`migration_settings.min_interval`), Planner его соблюдает;
  - **порог выигрыша Δmin**, мс, из формулы диплома — новый параметр Planner.
- Planner передаёт подтверждённые действия в исполнитель через
  `service.MigrationService.SubmitActions`, а не по HTTP. `action_id` действия =
  `recommendation_id`, `plan_id` = ID ревизии плана.

## Часть 1. Metadata: каталог для Planner

- `ListPlacementsRequest.include_noncurrent_hot` (bool): дополнительно вернуть
  нетекущие версии активных объектов с расположением HOT (`is_current = false`).
  Без флага поведение прежнее.
- `PlacementInfo.version_created_at` (Unix ms) — время создания версии. Нужно
  Feature Builder для возраста и перезаписей.
- Пагинация по `version_id` остаётся, нетекущие версии идут в том же порядке.
- Тесты: unit (handler, service) и integration на PostgreSQL. Объект с тремя
  версиями, из них одна старая в HOT. С флагом возвращаются текущая и старая из
  HOT, без флага — только текущая. Удалённый объект не возвращается.
- Документация: proto-комментарии, README Metadata, CLAUDE.md Metadata.

## Часть 2. SPPR: Planner и команды

### Снимок на начало цикла T

1. Каталог: `ListPlacements(include_noncurrent_hot=true)` целиком и
   `ListStorageClasses` из Metadata.
2. История: события и минутные агрегаты из БД SPPR за окно, нужное
   Feature Builder (сейчас 48 ч), и `Coverage` из `ingestion_streams`/`ingestion_gaps`.
   Нельзя держать в памяти миллионы `AccessEvent`: если Feature Builder требует
   события, допустимо собирать их из `read_aggregates` (минутная точность
   достаточна для признаков) или добавить в Feature Builder вход из агрегатов
   с тестом на совпадение признаков.
3. Ограничения SPPR: закрепления (`pins`), минимальный интервал (последний
   `succeeded` перенос версии), действия `pending`/`running` (версия занята),
   остаток бюджета `B` (`GetBudget`).

### Прогноз

`FeatureBuilder.Build` → `ewma.Predict(snapshot, H)` → `N̂_i`. Прогноз —
интерфейс `Predictor` (`Predict(snapshot, horizon) (DemandForecast, error)`),
чтобы на этапе 8 подставить ML. Доля чтения `r_i` = `Features.MeanReadFraction`,
если чтений не было — 1. `D̂_i = N̂_i · r_i · s_i`.

Если `DataQuality.Usable = false` хотя бы у общей истории (не у отдельного нового
объекта), цикл сохраняет ревизию со статусом `history_incomplete`, без
рекомендаций и с причиной. Новые объекты без истории получают прогноз 0 и
пометку в объяснении.

### Алгоритм (по тексту ВКР)

`L_i^j = N̂_i c_j + D̂_i / v_j`, `Δ_i = L_i^COLD − L_i^HOT`.

1. Ёмкость: `usable_j = u_j C_j`, где `u_j = min(u_j из настроек Planner,
   max_utilization из Metadata)`. Занято: `placed_bytes + copy_bytes` из Metadata
   плюс целевые копии ещё не начатых `pending` действий.
2. Если HOT переполнен уже в начале цикла, сначала выселить в COLD объекты HOT
   с наименьшим `Δ_i / s_i` (нетекущие версии — первыми, у них Δ = 0), пока не
   уложимся. Эти действия не требуют порога Δmin.
3. Незакреплённые и свободные объекты COLD — по убыванию `Δ_i / s_i`. Если места
   хватает, добавить перенос в HOT. Если не хватает, подобрать вытесняемые объекты
   HOT с наименьшим `Δ_i / s_i`. Замену включить, если
   `Δ_i − ΣΔ_вытесн − P · (s_i + Σs_вытесн) ≥ Δmin`, хватает бюджета `B` и места в
   COLD. Перенос в HOT зависит (`depends_on`) от всех своих вытеснений.
4. Перебор продолжается, пока есть кандидаты и бюджет. Отклонённый кандидат
   получает причину: `pinned`, `min_interval`, `in_progress`, `budget`,
   `cold_capacity`, `gain_below_threshold`, `no_forecast`.
5. Сложность O(n log n). Для проверки — точный перебор на малых задачах (≤ 12
   объектов) в тестах: при равных размерах и Δmin = 0 жадный план совпадает с
   точным, при разных размерах выигрыш жадного фиксируется в отчёте теста, но
   не требуется равным.

Параметры (config + страница настроек): `H` (`PLANNER_HORIZON`, 1h), `c_j` и `v_j`
(`PLANNER_HOT_C_MS`, `PLANNER_HOT_V_MIB_PER_MS`, то же для COLD; измеряются на
стенде на этапе 10, до этого — значения по умолчанию, записанные в README),
`P` (`PLANNER_PENALTY_MS_PER_MIB`), `Δmin` (`PLANNER_MIN_GAIN_MS`),
`u_HOT`/`u_COLD` (по умолчанию 0.9). Значения по умолчанию из руководства
администратора: 90 %, 256 МиБ бюджета, одна миграция, 60 мин интервала.

### Объяснение

Хранится вместе с рекомендацией (JSON), строится только из величин расчёта:
- действие: bucket/key/version, generation, исходный и целевой класс, размер;
- прогноз: метод (`ewma-1h-v1`), `N̂_i`, `r_i`, горизонт, качество данных,
  время с последнего чтения, чтения за 5m/1h/6h/24h, процентиль `N̂_i` в каталоге;
- эффект: `L^COLD`, `L^HOT`, `Δ_i`, штраф, чистый выигрыш, а для замен — что
  вытесняется и их `Δ`;
- ресурсы: занятость HOT/COLD до и после, расход бюджета, остаток;
- зависимости и причина отказа для отклонённых кандидатов.

Ожидаемый эффект хранится отдельно от измеренного: после выполнения действия
в объяснение не дописываются фактические цифры, они видны в журнале исполнителя.

### Хранение (миграция SPPR, up/down)

- `plans`: `plan_id`, `revision` (растёт), `created_at`, `trigger`
  (`timer`/`manual`), `status` (`ready`, `history_incomplete`, `failed`,
  `superseded`, `confirmed`, `rejected`), `method_version`, `horizon`, параметры
  расчёта, сводка (число действий, байты, суммарный выигрыш), `error`.
- `recommendations`: `recommendation_id` (UUID, он же `action_id`), `plan_id`,
  версия и `expected_generation`, классы, размер, `kind` (`promote`, `evict`,
  `rebalance`), `selected` (вошла в план) или причина отказа, explanation JSON.
- `recommendation_deps`.
- `admin_commands`: `command_id` (идемпотентный ключ клиента), тип (`confirm`,
  `reject`, `cancel_pending`, `pause`, `resume`, `settings`, `recompute`),
  инициатор (`user_id` из токена), `plan_id`, выбранные рекомендации,
  `status` (`accepted`, `rejected`), код ошибки, `created_at`.
- `planner_settings`: `u_HOT`, `u_COLD`, `P`, `Δmin`, `H`, `c_j`, `v_j`.

Хранить только последние `PLANNER_KEEP_PLANS` (по умолчанию 200) ревизий без
подтверждения, подтверждённые — всегда.

### Команды

- `ConfirmPlan(command_id, plan_id, recommendation_ids | all)`:
  - `plan_id` не последняя ревизия или статус не `ready` → `PLAN_STALE`;
  - выбранное действие зависит от невыбранного → `DEPENDENCY_REQUIRED` с
    перечнем недостающих; план не дополняется автоматически;
  - иначе одной транзакцией: команда `accepted`, план `confirmed`,
    `SubmitActions`. Ответ сразу, без ожидания переноса.
- `RejectPlan(command_id, plan_id)`.
- `CancelPending(command_id, plan_id | action_ids)` → `MigrationService.CancelActions`.
- `SetPaused(command_id, paused)`.
- `Recompute(command_id)` — внеочередной расчёт; не ждёт окончания, если расчёт
  уже идёт, возвращает его.
- Повтор с тем же `command_id` возвращает прежний результат; с другими полями — 409.
- Все команды пишутся в `admin_commands`, включая отклонённые.

### JSON API (префикс `/api/planner`)

`GET /plans` (страницы), `GET /plans/latest`, `GET /plans/{id}`,
`GET /plans/{id}/recommendations?selected=&kind=&page_token=&page_size=` (≤100),
`POST /plans/recompute`, `POST /plans/{id}/confirm`, `POST /plans/{id}/reject`,
`POST /commands/cancel-pending`, `POST /commands/pause`, `POST /commands/resume`,
`GET /commands`, `GET /commands/{id}`, `GET/PUT /settings`, `GET /status`
(занятость классов, качество истории, метод прогноза, состояние исполнителя и
последней ревизии). Коды ошибок из таблицы ВКР: `PLAN_STALE`, `CAPACITY_LIMIT`,
`BUDGET_EXHAUSTED`, `DEPENDENCY_REQUIRED`, `HISTORY_INCOMPLETE`,
`MODEL_UNAVAILABLE`, `ACCESS_DENIED` в теле ответа. Проверка прав в части 2 —
интерфейс-заглушка `Authorizer`, разрешающий всё; реальную реализацию
подключает часть 3.

### Конфигурация

`PLANNER_ENABLED` (по умолчанию false; таймер и API работают только с ним),
`PLANNER_INTERVAL`, `PLANNER_HORIZON`, `PLANNER_KEEP_PLANS`, параметры алгоритма
выше. Planner требует `MIGRATION_ENABLED=true`.

### Тесты части 2

- Unit алгоритма (таблично): пустой HOT; полный HOT и замена; замена невыгодна
  из-за P или Δmin; бюджет кончается посреди; закрепление, интервал, занятая
  версия; нетекущая версия в HOT выселяется; переполненный HOT в начале цикла;
  COLD без места для вытесняемого.
- Точный перебор против жадного (см. алгоритм).
- Объяснение согласовано с расчётом: суммы в объяснении = величинам плана (C-01).
- Команды (minimock): stale, dependency_required, повтор `command_id`, 409,
  частичное подтверждение с зависимостями, пауза.
- Integration PostgreSQL: ревизии и `superseded`, атомарность confirm + submit.
- Бенчмарк: 10 000 объектов и история 48 ч при 20 чтениях/с — расчёт ≤ 30 s и
  пик памяти ≤ 512 МиБ (записать фактические числа в PR).

## Часть 3. Доступ, HTML, сквозная проверка

### Доступ

- Middleware для `/api/*` и HTML: токен из `Authorization: Bearer` или cookie;
  `Auth.ValidateToken` → `user_id`; `AuthZ.Check(user, ADMIN, system:placement)`.
  Ответ `401`/`403` с кодом `ACCESS_DENIED`. `health` остаётся открытым.
- Вход в панель: форма логина → `Auth.Login` → `Auth.GetAccessToken`, токен в
  HttpOnly cookie. Выход — удаление cookie.
- `make seed-planner-admin`: создать пользователя-администратора и кортеж
  `HAS_PERMISSION ADMIN` на `system:placement` в AuthZ.
- `AUTH_GRPC_ADDR`, `AUTHZ_GRPC_ADDR` в конфиге SPPR; без них при
  `PLANNER_ENABLED=true` сервис не стартует.

### HTML (серверные шаблоны Go, без JS-фреймворков)

Страницы из руководства администратора: «Состояние», «Настройки» (Planner +
бюджет/интервал/пауза исполнителя + закрепления), «Рекомендации» (ревизия,
метод, фильтры, карточка с объяснением и зависимостями, выбор, «Подтвердить»,
«Отклонить план», «Рассчитать план»), «Команды», «Миграции» (журнал действия до
очистки). Ошибки показываются расшифровкой и допустимым действием, а не только
кодом. Формы с `command_id`, чтобы повтор отправки не создавал новую команду.

### Сквозная проверка `make smoke-planner`

Стенд Gateway + Metadata + Storage HOT/COLD + Kafka + SPPR (Planner, исполнитель)
+ Auth + AuthZ:
1. PUT N объектов (COLD), частые GET по части из них.
2. `POST /plans:recompute` → в плане перенос востребованных объектов в HOT.
3. Подтверждение без прав → 403 (C-04). Подтверждение входа в полный HOT без
   вытеснения → `DEPENDENCY_REQUIRED` (C-02). Подтверждение старой ревизии →
   `PLAN_STALE` (C-03).
4. Подтверждение допустимого плана → действия `succeeded` → GET из HOT, те же байты.
5. Спрос сменился → новый план выселяет остывшие объекты в COLD (обратный перенос).
6. Путь одной версии виден в журнале: рекомендация → команда → миграция (C-06).

## Расхождения с текстом

Заполняется по ходу работы.
- Часть 3 сохраняет `system:placement`: AuthZ runtime не ограничивает префиксы,
  `infer_node_label` возвращает `Resource` для неизвестного префикса. Формат
  в комментарии proto перечисляет только bucket/object, но это не runtime-запрет;
  AuthZ не изменён.
- Доступ по умолчанию наследует `PLANNER_ENABLED`; явное
  `ADMIN_AUTH_ENABLED=false` оставлено для локальных тестов с warning. При
  включённой проверке адреса Auth/AuthZ обязательны; сбои дают 503.
- Существующий MigrationService не принимает command_id для бюджета, интервала и
  pins. HTML оборачивает эти методы транзакционным журналом
  `admin_form_commands` с advisory lock; две группы команд видны на одной странице.
  Planner/executor и их алгоритмы не менялись.
- При смене спроса smoke усиливает чтения второго объекта (120 против 12 у первого),
  чтобы проверить замену по EWMA без ожидания часа: первый становится относительно
  холодным. Это проверка управления, а не измерение точности/ускорения.

- В тексте Δmin — порог выигрыша, а в исполнителе 4.3 этим именем назван
  минимальный интервал. В коде и документации исполнителя переименовать нельзя
  без миграции; в тексте ВКР и интерфейсе использовать «минимальный интервал».
- Пути `…:confirm` заменены на `…/confirm`: стандартный маршрутизатор Go не
  поддерживает суффикс после параметра пути.
- Зависимое действие исполнитель берёт, когда предшественник `succeeded` и его
  источник удалён (в ТЗ 4.3 — только `succeeded`). Иначе перенос в HOT после
  вытеснения упирался бы в место, которое старая копия держит до очистки
  (`failed/no_capacity`). Это совпадает с текстом ВКР: «копии в HOT удалены».
- Metadata переносит нетекущую версию активного объекта только в COLD (часть 1):
  без этого Planner видел бы старые версии в HOT, но не мог их выселить.
- Вытеснение выбирает лучший из двух вариантов (по `Δ/s` в пределах бюджета и
  один объект с наименьшей потерей) и дозаполняет освобождённое место следующими
  кандидатами. По тексту ВКР — только вытеснение по `Δ/s`. На случайных задачах с
  разными размерами это подняло долю оптимальных планов с 81 % до 89 %, средняя
  доля оптимума 97,7 %; для равных размеров результат тот же (точный).
- Остаток бюджета тратится на выселение перезаписанных версий из HOT
  (`evict_noncurrent`), хотя по формуле их выигрыш отрицателен: решение автора
  27.10 — старые версии не должны занимать HOT.
- Пока нет heartbeat (этап 5), история считается полной до T и начатой не позже
  самой старой версии каталога; найденные Ingestor пропуски по-прежнему
  останавливают планирование (`history_incomplete`).
- Признаки строятся из минутных агрегатов, а не из сырых событий: сутки при
  20 чтениях/с — 1,7 млн событий против ~670 тыс. строк агрегата. Для событий в
  начале минуты признаки совпадают точно (тест), иначе время округлено до минуты.
- Переполненный HOT в начале цикла разгружается без порога Δmin, иначе план был
  бы недопустимым по условию ёмкости.

## Что понять автору (из плана)

Почему самый популярный объект не всегда надо переносить (большой размер →
малый `Δ/s`, штраф P, порог Δmin, бюджет) и почему хороший прогноз не даёт
немедленной выгоды (смена набора из K объектов занимает не меньше `2Ks/B` циклов).

## Не делать

- ML и обучение (этап 8), heartbeat и полноту W (этап 5).
- Автоматическое применение плана без подтверждения.
- Отдельный сервис объяснений, JS-фреймворки, новые сервисы в Compose кроме
  уже существующих Auth/AuthZ.
