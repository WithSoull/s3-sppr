# Шаг 6: данные, признаки и EWMA

Дата проверки: 27.10.2026. Это реализация автономной части шага 6 плана
предзащиты. Данные синтетические; обучение модели и результаты эксперимента здесь
не заявляются. Приёмка автором ещё предстоит.

## Что работает

Один Go-компонент `service.FeatureBuilder` рассчитывает признаки для учебного
примера и синтетической выборки. Тот же интерфейс доступен в service provider
для дальнейшего подключения к серверу. Расчёт не зависит от Kafka, PostgreSQL,
класса хранения или скрытой популярности генератора. Входная история должна
быть уже дедуплицирована Ingestor.

CLI создаёт каталог версий, события за семь логических суток, срезы с часовыми
метками и EWMA. Выгрузка потоковая; в памяти остаются сутки истории и следующий
час для меток, а также два последних более старых чтения каждой версии для
давности обращений. Это ограничивает рост памяти по длительности прогона;
выполнение ресурсной квоты на основном профиле пока не измерено.

К F-03 относятся расчёт по прошлому, признаки полноты и исключение непригодных
строк. Для F-12 подготовлены EWMA и общий формат прогноза. Работа F-03 с живой
историей и автоматическое переключение модели по F-12 ещё не проверены.

## Учебный пример

Из корня репозитория:

```bash
make demo-sppr-data
```

Момент T — `2026-10-22T12:00:00Z`, горизонт — час. Все размеры — 100 байт.
Каталог и все восемь событий заданы в `dataset.Lesson`.

| Версия | Что известно к T | Признаки | Метка `[T,T+1ч)` |
|---|---|---|---|
| a1 | Создана сутки назад; клиентские чтения в 11:00 на 100 байт и 11:30 на 50 байт | `reads_1h=2`, `reads_5m=0`, давность 1800 и 3600 с, средняя доля 0,75 | 2: в 12:00 и 12:59 |
| b1 | Создана сутки назад; чтений нет | Числа чтений и EWMA равны 0; давности равны `null` | 0, `has_read=false` |
| c1 | Создана в 11:45; чтение в 11:55 | `reads_5m=1`, наблюдаемая история 900 с, качество `warmup` | 1: в 12:05 |

Техническое чтение a1 в 11:59 не увеличивает спрос. Чтение a1 ровно в 13:00
не входит в эту метку. Будущая версия `f1`, создаваемая в 14:00, не входит в срез.
Удаление c1 в 12:10 не удаляет её строку из прошлого среза. У бакета перед T
три клиентских чтения за час; активны две из трёх существующих версий.

EWMA — экспоненциальное сглаживание потока событий с нулевой начальной
интенсивностью. Для периода полураспада τ и возраста чтения a в часах вклад
в оценку чтений за час равен `(ln(2)/τ) * exp(-ln(2)*a/τ)`. Суммируются чтения
за последние 24 часа; более старый вклад отбрасывается по версии правил v1.
Для a1 при τ=1 получаем `ln(2)*(0,5+sqrt(0,5)) ≈ 0,836702662`.
При другом горизонте оценка умножается на его длительность в часах.
Это прогноз, поэтому он не обязан совпадать с фактической меткой 2.
При короткой истории сглаживание начинается с нуля; `warmup` сохраняется явно.

## Зафиксированные правила признаков

Версия — `features-v1`. Окна полуоткрытые: `[T-L,T)`. Событие ровно в T
принадлежит метке. Используются только `read/client/success`; запись,
внутреннее копирование и ошибка не увеличивают спрос.

| Поля в `snapshot.features` | Правило |
|---|---|
| `log_size`, `age_seconds` | `ln(1+size_bytes)` и возраст существующей версии |
| `overwrites_24h` | Создания следующих версий того же ключа за 24 ч строго до T; первое известное создание не считается перезаписью |
| `last_read_seconds`, `previous_read_seconds` | Давность двух последних клиентских чтений; `null`, если чтения неизвестны |
| `reads_5m`, `reads_1h`, `reads_6h`, `reads_24h` | Числа чтений в соответствующих окнах |
| `ewma_1h`, `ewma_6h` | Оценки чтений за час с полураспадами 1 ч и 6 ч |
| `short_long_ratio` | `(reads_5m / 5) / (reads_1h / 60)`; 0 при нулевом знаменателе |
| `reads_day_ago` | Чтения за `[T-24ч,T-23ч)` |
| `mean_read_fraction` | Среднее `bytes/size_bytes` за 24 ч; 0 без чтений или у пустой версии |
| `bucket_reads_1h` | Все клиентские чтения бакета за час, включая версии, удалённые до T |
| `bucket_active_fraction` | Доля существующих в T версий бакета с чтением за час |
| `observed_seconds` | Известная наблюдаемая длительность, ограниченная возрастом и 24 ч |

Размер и идентичность версии сохраняются в срезе. Момент последующего удаления,
параметры групп и будущий всплеск в срез не передаются. Будущий ML Trainer должен
использовать только `snapshot.features`, отбирать `eligible=true` и сохранять
версию правил. Идентификаторы, прогноз EWMA, split, метка и manifest не являются
входными признаками модели.

## Полнота и ошибки

`Coverage` задаёт начало наблюдений, подтверждённую общую границу W и интервалы
пропусков. `MAX(occurred_at)` или прогресс одного потока эту границу не заменяют.
В синтетическом воспроизведении генератор подтверждает полноту до T; завершённая
история отдельно подтверждает интервалы меток. Будущая граница не передаётся
как признак модели.

При неизвестной полноте возвращается `unknown_completeness`, при W<T —
`watermark_behind`, при пропуске — `gap`, при отсутствии необходимого начала
наблюдений — `unobserved`. Такие строки сохраняются, но не допускаются к обучению.
Проверка пропусков консервативна для всего наблюдаемого каталога, поскольку
вектор включает статистику бакета. Неполные интервалы не подменяются нулями.

У нового объекта известная короткая история помечается `warmup`; ровно в момент
создания — `no_history`. Такой холодный старт пригоден как наблюдаемый пример,
но не доказывает нулевой будущий спрос. Это отличается от старого объекта,
историю которого не собирали. У полностью наблюдавшегося объекта без чтений
ноль является известным отсутствием спроса.

Метка известна только если весь `[T,T+1ч)` завершился не позже W и не пересекает
gap. Иначе `reads` и `has_read` равны `null`, а не 0/false. `available_at` —
конец горизонта, то есть самое раннее время готовности при своевременной доставке.
Для следующего этапа обновления модели нужно также проверять фактическую W.

Некорректный каталог, отрицательные байты, чтение больше версии, неверная
геометрия coverage или несовместимая версия правил возвращают ошибку.
EWMA проверяет конечность и неотрицательность результата. Если данные
непригодны, численная оценка сохраняется для диагностики вместе с
`quality.usable=false`; Planner обязан проверять этот флаг.

## Генератор и выборка

```bash
make dataset-sppr
make dataset-sppr SPPR_SCENARIO=shift SPPR_SEED=1 SPPR_DATA_OUT=build/sppr-shift-1
```

Назначение должно отсутствовать. CLI создаёт временную папку рядом с ним,
публикует законченный результат переименованием и удаляет временные файлы
при ошибке или отмене. Новые переменные окружения сервера, миграции БД,
protobuf, моки и внешние зависимости для этой части не нужны.

| Файл | Содержание |
|---|---|
| `catalog.json` | Каталог с размером, созданием и удалением каждой версии; это вход симуляции, а не вектор ML |
| `events.jsonl` | Исходные успешные клиентские чтения в модели `AccessEvent` по логическому времени; это JSON, не Kafka protobuf |
| `slices.jsonl` | Неизменяемые срезы, прогнозы, split, отдельные метки и допуск `eligible` |
| `manifest.json` | Эффективная конфигурация, границы периодов, версии, SHA-256 файлов и конфигурации, git HEAD, хеш исходников SPPR и версия Go |

`small.json`: 20 объектов, 0,01 чтения/с, срез раз в час. Две версии появляются
через сутки, две удаляются через четверо суток. Это учебная проверка жизненного
цикла. `acceptance.json`: 10 000 объектов по 1 МиБ, 20 полных чтений/с,
срез раз в 300 с, фиксированный каталог. Этот профиль даёт 12 096 000 обращений
и 20 160 000 строк за сценарий; файлы занимают много гигабайт.

```bash
make dataset-sppr SPPR_DATA_CONFIG=services/sppr/examples/data/acceptance.json \
  SPPR_SCENARIO=stable SPPR_SEED=0 SPPR_DATA_OUT=build/sppr-acceptance-stable-0
```

Версия генератора — `synthetic-v1`; PRNG — Go `math/rand/v2` PCG. Для основной
серии предназначены seed 0…9, одинаковые для всех политик. `start` и все параметры
задаются в JSON, фактически использованные значения попадают в manifest.
Параметры распределений ниже — исходный воспроизводимый профиль, который нужно
принять до обучения и итоговой проверки. Они не подбирались по качеству модели.

Внутренний порядок объектов перемешивается по seed. Основной популярный набор
содержит 10% каталога. С вероятностью p выбирается объект этого набора, иначе —
равномерно из всего активного каталога. Поэтому фактическая доля популярных
объектов при p=0,8 и доле набора 0,1 близка к 0,82, а не ровно 0,8.
При включённом lifecycle несуществующий объект перевыбирается.

| `scenario` | Правило |
|---|---|
| `stable` | Постоянные набор и p=0,8 |
| `decay` | p=0,8·exp(-t/24ч), интерес постепенно снижается |
| `periodic` | p=0,8·(1+cos(2πt/24ч))/2 |
| `burst` | p=0 вне одного всплеска; p=0,8 с 100-го часа в течение 30 мин |
| `shift` | p=0,8; каждые 24 ч выбирается следующий непересекающийся набор |
| `uniform` | p=0, независимый равномерный выбор активного объекта |

Параметры p, размера набора, затухания, периода, всплеска и смены набора
настраиваются в конфигурации. Генератор задаёт моменты поступления с постоянной
частотой. Очереди, конкурентность восьми запросов, длительность чтений и переносы
относятся к будущему симулятору/стендовому генератору шага 10.

Границы относительно `start`: train `[0,48ч)`, validation `[48,72ч)`, test
`[72,168ч)`. Допуск требует `T+1ч <= конец периода`. Пример в 47:00 допустим
для train, в 47:05 — `purged`, в 48:00 — validation. Аналогично очищаются
границы validation и конца доступной истории. Строки `purged` сохраняются для
аудита. Метки не продолжаются в следующий период. Итоговый тест не используется
для выбора правил или параметров.
