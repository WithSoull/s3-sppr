# Этап 9: обновление модели и журнал версий

Сейчас SPPR загружает одну модель из `PLANNER_MODEL_DIR` при старте и откатывается
на EWMA, если она не подходит (этап 8). Этап 9 добавляет регулярное переобучение
на собственной истории хранилища, проверку и горячую замену модели, журнал
версий и правила устаревания. Причина, по которой это нужно, видна на стенде:
модель профиля приёмки даёт объекту без чтений `N̂ = 1,49`, а модель, обученная
на истории самого стенда, такой ошибки не сделает.

## Решения

1. **Реестр и журнал.** Каталоги моделей лежат в `PLANNER_MODEL_REGISTRY`
   (`<registry>/<model_version>/` — те же четыре файла «Схемы файлов экспорта
   v1»). Таблица `model_versions`: `model_version` (PK), `status`
   (`candidate`, `active`, `rejected`, `retired`), `reason`, `source`
   (`bootstrap`, `scheduled`, `manual`), `trained_from`, `trained_to` (конец
   данных с метками), `train_rows`, `train_seconds`, `validation_cov_k`,
   `validation_ewma_cov_k`, `created_at`, `activated_at`, `retired_at`.
   Каждая попытка обучения, включая неудачную, — строка журнала (неудача без
   каталога получает служебную версию `failed-<время>`). Ревизия плана уже
   хранит `model_version`, поэтому путь объекта и версия модели восстанавливаются
   по журналу.
2. **Начальная модель.** Если журнал пуст и задан `PLANNER_MODEL_DIR`, модель
   импортируется в реестр как `bootstrap` и проходит те же проверки. Иначе SPPR
   работает на EWMA до первой успешной модели.
3. **Горячая замена.** `ModelManager` хранит текущий предиктор за атомарным
   указателем. Цикл Planner берёт предиктор в начале расчёта и заканчивает
   расчёт на нём, даже если модель сменилась посередине.
4. **Проверки перед включением** (иначе `rejected` с причиной, текущая модель
   остаётся): загрузка `lgbm.Load` (SHA-256, схема, имена и порядок признаков,
   горизонт = горизонт Planner, контрольные строки Python/Go), затем прогноз по
   последним признакам каталога — все выходы конечны и неотрицательны.
5. **Устаревание.** Возраст модели — `now − trained_to`. Больше
   `PLANNER_MODEL_MAX_AGE` (по умолчанию 72 ч) — Planner переходит на EWMA с
   причиной `model_stale` (в журнал), модель не удаляется; следующая успешная
   модель снова включает ML.
6. **Расписание.** Попытка раз в `PLANNER_MODEL_UPDATE_EVERY` (24 ч) и по
   команде администратора (`POST /api/planner/model/retrain`, с `command_id`,
   журнал `admin_commands`, кнопка в `/admin`). Одновременно идёт не больше
   одного обучения. Попытка не начинается, пока полной истории меньше
   `PLANNER_MODEL_MIN_HISTORY` (по умолчанию 26 ч: окно признаков 24 ч + горизонт
   + запас); в журнал это не пишется, только в статус.
7. **Данные для обучения.** Новый `dataset.FromHistory`: каталог из Metadata
   (`ListPlacements`), минутные агрегаты и `Coverage` из БД SPPR (W этапа 5) —
   тот же путь, что у прогноза Planner (минутные агрегаты, `features.Build`).
   Срезы раз в 15 мин, выровнены по минуте, за последние
   `PLANNER_MODEL_TRAIN_WINDOW` (7 сут). Метка — сумма чтений минут `[t, t+H)`;
   срез берётся, только если признаки и метка пригодны (`W ≥ t+H`, нет пропусков
   в окне — `features.Quality`). Train — всё, кроме последних 1/7 окна;
   validation — последние 1/7; test пуст. Удалённые за окно версии в каталоге
   Metadata уже не видны — ограничение записывается в манифест набора.
8. **Обучение.** Отдельный процесс `PLANNER_TRAIN_COMMAND` (по умолчанию
   `python -m sppr_ml train --data {data} --out {out} --params {params}`) с
   таймаутом `PLANNER_MODEL_TRAIN_TIMEOUT` (30 мин). Гиперпараметры — из
   манифеста активной модели, иначе значения по умолчанию
   (`num_leaves 15, learning_rate 0.03, min_data_in_leaf 20, lambda_l2 1.0`),
   без перебора сетки. Ошибка, таймаут, нулевой выход или модель без
   регрессора — неудача в журнале, текущая модель остаётся. Обучение не
   блокирует приём событий и расчёт планов. `validation_cov_k` модели и EWMA
   пишутся в журнал для сведения, не как фильтр.
9. **Горизонт.** Python-пакет берёт горизонт из манифеста набора
   (`horizon_seconds`), а не из константы, и пишет его в манифест модели. Для
   стенда это позволяет короткий горизонт (`PLANNER_HORIZON=2m`); признаки
   `features-v1` не меняются.
10. **Образ SPPR.** Финальный образ содержит Python 3.12, пакет `sppr_ml` и
    зависимости из `requirements.txt` (плюс `libgomp`), чтобы обучение шло внутри
    квоты SPPR (2 ядра / 2 ГиБ, `num_threads=2`). Compose: том для реестра
    (`/models/registry`, запись), `./build/models` остаётся только для импорта.
11. **Видимость.** `/api/planner/status` и `/admin`: активная модель, источник,
    возраст, предел возраста, причина EWMA (если ML выключен), последняя
    попытка (время, итог, причина), следующая плановая попытка, ход текущего
    обучения. Страница журнала версий в `/admin`.

## Проверка

- Unit с управляемыми часами и подменой команды обучения: успешная замена;
  несовместимая модель (горизонт, имена признаков, контрольные строки) →
  `rejected`, текущая остаётся; NaN в прогнозе → `rejected`; ошибка и таймаут
  обучения → неудача в журнале, текущая остаётся; устаревание → EWMA, новая
  модель → снова ML; цикл Planner, начатый на версии A, заканчивается на A при
  замене на B; рестарт восстанавливает активную модель из журнала и реестра.
- `dataset.FromHistory`: метки только при `W ≥ t+H`, пропуск исключает срезы,
  выравнивание по минуте, совпадение признаков с расчётом Planner на тот же
  момент.
- Python: горизонт из манифеста набора; тесты пакета.
- Стенд, `make smoke-ml-update` (`PLANNER_HORIZON=2m`,
  `PLANNER_MODEL_MIN_HISTORY` и окно — минуты): нагрузка чтениями → обучение по
  команде администратора → новая версия активна → план с этой версией →
  подтверждение → перенос → чтение; затем подмена команды обучения на падающую
  → неудача в журнале, план продолжает строиться на прежней версии.
- Документация: README SPPR (конфигурация, реестр, журнал), `.env.example`,
  AGENTS.md, CLAUDE.md, `docs/ml-spec.md` (горизонт из манифеста).
